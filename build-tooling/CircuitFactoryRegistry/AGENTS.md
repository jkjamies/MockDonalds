# CircuitFactoryRegistry (Build-Time Codegen)

## Purpose

Build-time SwiftSyntax codegen tool that scans `iosApp/` for SwiftUI views annotated with `@CircuitInject` and emits `iosApp/iosApp/Generated/GeneratedCircuitFactories.swift`. The generated file is consumed by `AppDelegate.swift` via `CircuitIos.generatedFactories()` — replacing what would otherwise be a hand-maintained registration table that drifts out of sync as screens are added.

## Why It Lives Here (not in `iosApp/`)

Xcode's iOS build environment exports `SDKROOT=iphonesimulator…` into Run Script Phases. If this executable's SwiftPM manifest were nested inside `iosApp/`, `swift build` invocations would inherit that env and try to evaluate a macOS manifest against the iOS SDK, failing with the cryptic `error: 'circuitfactoryregistry': Invalid manifest`. Keeping the package under `build-tooling/` (outside the iOS project root) plus an explicit `unset SDKROOT PLATFORM_NAME EFFECTIVE_PLATFORM_NAME TARGET_DEVICE_PLATFORM_NAME TOOLCHAINS` at the top of the Run Script Phase keeps SwiftPM evaluating the macOS manifest with a macOS SDK.

## How It Works

1. **Run Script Phase** in `iosApp/project.yml` (`Generate Circuit factory registry`):
   - `unset` Xcode's iOS-build env vars
   - `cd build-tooling/CircuitFactoryRegistry`
   - `swift build -c release --product CircuitFactoryRegistry`
   - `find iosApp/iosApp -name '*.swift' -not -path '*/Generated/*' -print0 | CircuitFactoryRegistry --paths-from-stdin --output iosApp/iosApp/Generated/GeneratedCircuitFactories.swift`

   The list is piped through stdin rather than `xargs` so the generator runs in a single invocation regardless of project size — `xargs` would fan out into multiple invocations once the path list exceeds `ARG_MAX`, and each invocation truncates the output file, silently dropping earlier entries.

2. **`RegistryGenerator.generate(sourcePaths:)`** parses each `.swift` file with `SwiftParser` and walks it with `CircuitInjectVisitor`.

3. **`CircuitInjectVisitor`** (a `SyntaxVisitor`) collects `CircuitInjectEntry { viewType, screenType, stateType, isDebugOnly }` for every `@CircuitInject(Screen.self, State.self)` attached to a `struct`, `class`, or `actor` declaration. It tracks `IfConfigDeclSyntax` nesting so views wrapped in `#if DEBUG` are flagged as debug-only without requiring an explicit argument on the macro.

4. **`RegistryEmitter.emit(entries:)`** sorts entries (debug-only last), emits the file:
   ```swift
   // Generated by CircuitFactoryRegistryPlugin. Do not edit.
   import SwiftUI
   import ComposeApp

   extension CircuitIos {
       static func generatedFactories() -> [UiFactory] {
           var factories: [UiFactory] = [
               ScreenUiFactory<HomeScreen, HomeUiState> { HomeView(state: $0) },
               // …
           ]
           #if DEBUG
           factories.append(ScreenUiFactory<DebugScreen, DebugUiState> { DebugView(state: $0) })
           #endif
           return factories
       }
   }
   ```

5. **`AppDelegate.swift`** calls `CircuitIos.generatedFactories()` to construct `CircuitIos`. No hand-edits — adding `@CircuitInject` to a new view automatically wires it in on the next build.

## Annotated View Contract

Generated lines call `ViewName(state: $0)` directly, so every annotated view must expose `init(state: SomeUiState)`. `Harmonize` enforces SwiftUI view conventions; the registry assumes they hold.

## `#if DEBUG` Detection

The visitor increments `debugDepth` when entering an `#if DEBUG` clause and decrements on exit. Any `@CircuitInject` declared while `debugDepth > 0` is marked `isDebugOnly`, and the emitter places it inside the trailing `#if DEBUG` block of the generated registry. Views inside `#if DEBUG` thus stay debug-only without polluting the macro signature.

## Build & Test

```bash
cd build-tooling/CircuitFactoryRegistry
swift build                                                    # Compile (debug)
swift test                                                     # Run the test suite
swift build -c release --product CircuitFactoryRegistry        # Same flow Xcode runs
```

The Run Script Phase runs on every build (`basedOnDependencyAnalysis: false`) — it's fast (incremental SwiftPM build + a parse-only walk over ~60 source files) and required for the iOS app to compile.

## Why a Separate Codegen Tool Instead of the Macro?

Swift macros operate on a single declaration in isolation. Aggregating across files into a single registry table requires walking the whole module — exactly what a build-time SwiftSyntax tool does well, and exactly what the macro system is not designed for. Splitting responsibilities cleanly: `CircuitMacros` validates the call site at compile time; `CircuitFactoryRegistry` aggregates across sites at build time.
